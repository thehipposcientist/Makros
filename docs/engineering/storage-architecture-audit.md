# Storage Architecture Audit

Date: 2026-05-23

Scope: searched the app, shared modules, watch target, backend references, and docs for `AsyncStorage`, `SecureStore`, `localStorage`, `MMKV`, `persist(`, `createJSONStorage`, `persistQueryClient`, `createAsyncStoragePersister`, `UserDefaults`, and manual JSON persistence.

Result: no `localStorage`, MMKV, Zustand persist middleware, Redux persist, or React Query persisted cache were found. The app uses AsyncStorage/manual JSON caches on React Native and UserDefaults on watch/native bridge.

## Highest Risk Findings

| Finding | Risk | Files | Fix made |
|---|---:|---|---|
| Opaque `/profile/state` sync pushed canonical user data from AsyncStorage (`userProfile`, plans, meal edits/checks, routines, workout history, goals, body history) and later rehydrated it as if durable. | High | `app/index.tsx` | Yes. The sync allowlist is now empty, legacy canonical blobs are quarantined under `legacyCanonicalStateQuarantine_v1`, and remote state is overwritten with a DB-source marker. |
| Persistent read-cache keys included the raw bearer token in AsyncStorage key names. | Critical | `src/services/api.ts` | Yes. New cache namespace is `read_cache_v2::`; token scope is hashed, and legacy `read_cache_v1::*` keys are removed. |
| Meal routine edits in profile wrote only the local `mealRoutines` cache. | High | `src/screens/EditProfileScreen.tsx`, `src/utils/mealRoutineSync.ts` | Yes. The screen now loads/saves through meal routine API reconciliation when authenticated, preserves `backendId` in edit mode, and server rows win on sync. |
| Workout completion retry path could duplicate rows when retried without a stable external source id. | High | `src/utils/workoutCompletionQueue.ts`, `src/services/api.ts`, `backend/app/routers/workouts.py`, `backend/app/models.py`, `backend/app/database.py` | Yes. Completion requests now carry idempotency keys; backend has idempotency column and unique partial indexes. |
| User-set macro targets could live only inside cached profile JSON. | High | `backend/app/models.py`, `backend/app/database.py`, `backend/app/routers/profile.py`, `src/services/api.ts` | Yes. Added durable `UserPreferences.custom_macros`, sync serialization, startup migration, and regression coverage. |
| Legacy user-state hydration could recreate stale local canonical rows after DB tables were introduced. | High | `app/index.tsx`, `src/utils/storageKeys.ts` | Yes. Canonical keys are no longer restored through the blob; old data is quarantined instead of silently trusted. |

## Code Changes Made

- Added `src/utils/storageKeys.ts` with central key constants and explicit entity-type terminology.
- Added `src/utils/__tests__/storageKeys.test.ts` and included it in `scripts/run-frontend-tests.mjs`.
- Stopped `/profile/state` from syncing canonical AsyncStorage keys; added quarantine for legacy canonical blobs.
- Migrated persistent read cache to `read_cache_v2::` with hashed auth scope and cleanup of legacy raw-token keys.
- Added workout completion idempotency from client queue to backend model/router/database migrations.
- Added backend idempotency regression coverage in `backend/tests/test_workout_completion_idempotency.py`.
- Added durable `UserPreferences.custom_macros` with migration and profile sync regression coverage.
- Updated meal routine edit/delete in `EditProfileScreen` to reconcile with backend routine rows and preserve `backendId`.
- Changed meal routine sync so DB-backed rows win over stale local cache on matched routines.
- Marked meal/workout local stores as cache/draft in comments where they are still used for hot/offline rendering.

## Remaining Product Decisions

- `periodSymptomLogs_v1` is still local-only. If period/symptom history is expected to sync, it needs a backend table.
- `activeWorkout*` is still Option B: local crash recovery. That is acceptable only because completion now uses an explicit idempotent DB path.
- `weightHistory` and `bodyScanHistory` remain local caches in utility paths even though DB APIs exist. They should be tightened in a follow-up so authenticated writes are server-first everywhere.
- A few low-risk preference keys still use local string constants instead of `STORAGE_KEYS`. The high-risk canonical/cached entity keys are centralized now.
